# St. John Fisher University Catalog Intelligence Platform — Handoff Guide

This document serves as the technical handoff guide for the St. John Fisher University (SJFU) Catalog Intelligence Platform. It outlines the architecture, the upstream vendor mirror/override system, auditability mechanisms, verification harness execution, and database safety protocols.

---

## 1. System Architecture Overview

The system consists of three primary components:

1. **Web Application Frontend (`src/`)**: A Next.js 16 application providing the catalog editor, graph visualization, assistant interface, tracking dashboard, and PDF production wizard.
2. **Catalog Intelligence Swarm (`services/swarm/`)**: A FastAPI microservice responsible for catalog ingestion, semantic chunking, graph patching, and LLM-assisted corrections.
3. **Verification Harness (`verification_harness/`)**: An offline, multi-tier audit harness that evaluates extracted catalog data against original source page markdowns.

---

## 2. Code Ownership

**Every file in this repository is owned by this project.** There is no vendored directory, no
upstream mirror, and no synchronization step. Edit any file directly.

This is worth stating explicitly because earlier revisions of this document said the opposite. The
platform began as an adaptation of an existing catalog application, and for a time part of the
backend and a set of frontend files were maintained as pinned mirrors of that upstream repository,
guarded by lock files and a drift-reporting script. That relationship has been removed in full: the
backend was folded into `services/swarm/main.py` as ordinary source, the lock files and the sync
script were deleted, and no external repository is required to build, run, or modify this project.

Two consequences worth knowing:

- **The generation client is deliberately named for a history it no longer has.** The agents in
  `services/swarm/main.py` are written against an Anthropic message-shaped API, and
  `_anthropic_client()` returns the Vertex shim in `services/swarm/overrides/vertex.py`, which
  presents that same surface while calling Vertex Gemini with Application Default Credentials.
  There is no Anthropic key path in this deployment. If you change the generation provider, that
  shim is the single place to do it.
- **The brand surface is documented rather than enforced.** `docs/BRAND_SURFACE.md` lists the files
  that carry institution-specific presentation (theme, tokens, copy, favicon). Nothing prevents you
  from editing them — the list exists so that a future re-skin knows where to look.

### Institution-specific configuration

Institution identity is configuration, not code. `institution.config.yaml` holds the tenant, brand,
and host settings, and the swarm's correction prompt is parameterized on `INSTITUTION_LEGAL_NAME`
rather than naming an institution inline.

## 3. Data Storage & Provenance Strategy

The platform utilizes a dual-storage model:

- **Production Database (Supabase PostgreSQL)**: Stores the catalog schema — `documents`, `courses`, `programs`, `semantic_chunks`, `program_requirements`, `program_requirement_courses`, `corrections`, and related lookup tables (see `supabase/migrations/`). Configured via `DATABASE_URL`.
- **Local Triage Index (SQLite)**: The harness appends findings to `verification_harness/artifacts/findings.jsonl` and rebuilds a derived, queryable index at `verification_harness/artifacts/findings.sqlite` after every run (`report/sqlite_loader.py`). Both are local artifacts; the harness never writes to the production database (the sole write path is the remediation tool, §5).

### Tracing LLM Findings to Ground Truth

Every finding generated by the verification harness is fully auditable back to source markdown:

1. Open `verification_harness/artifacts/findings.jsonl`, or query the `findings.sqlite` triage index.
2. Locate the finding's `id` and associated `page` number (the source page in the cached markdown under `verification_harness/artifacts/page-cache/`).
3. Inspect `evidence_page` and `evidence_db`:
   - `evidence_page`: Quoted verbatim excerpt from original catalog markdown (page number corresponds to page markdown file index).
   - `evidence_db`: Database text representation evaluated during check.
4. **Evidence Validation**: All Tier 2 findings pass through `excerpt_supported()` in `verification_harness/checks/semantic/core.py`, which validates 5-token normalized shingles against source markdown. If the excerpt cannot be verified on the page, the finding's verdict is automatically demoted to `AMBIGUOUS`.

## 4. Verification Harness & Check Execution Tiers

The harness audits catalog extracted data in three distinct tiers:

### Tier 1 — Deterministic Checks

Runs fast, rule-based validations requiring zero LLM calls:

- `coverage.py` (Checks A1–A6): Course/program coverage, unlinked pages, ghost rows.
- `fidelity.py` (Checks B1, B4–B6): Field fidelity — credits, prerequisites, description formats.
- `titles.py` (Check B2): Deterministic title abbreviation matching and equivalence.
- `provenance.py` (Checks C1–C7): Source-page provenance — URLs, page links, content hashes.
- `headings.py` (Checks D1–D8): Heading and section-header structure.
- `integrity.py` (Checks E1–E4): Row integrity — e.g., staff bios or section headers mis-ingested as programs.

### Tier 2 — LLM Adjudication (`semantic/` package)

Adjudicates complex semantic questions requiring LLM reasoning (via Vertex AI / Gemini):

- `semantic/courses.py` (`check_b3_b4_f1`): Adjudicates course description truncation/bleed and course identity.
- `semantic/programs.py` (`check_b7_f2`): Adjudicates program credit totals and page aboutness.
- `semantic/chunks.py` (`check_f3`): Verifies chunk content matching section header breadcrumbs.
- `semantic/residue.py` (`check_b2_residue`): Adjudicates title abbreviation residue.
- `semantic/discovery.py` (`check_f4`): Bounded discovery of unanticipated defect classes (`info` severity only).

### Tier 3 — Adversarial Refutation & Reporting

- `adversarial.py`: Attempts to refute Tier 2 findings with counter-prompts; a finding that survives refutation is upgraded, one that does not is demoted. This reduces (but cannot eliminate) false positives ahead of human triage.
- `report/report.py`: Generates human-auditable HTML and Markdown summary reports.

## 5. Peer-Review Protocol & Safety Model

When remediating findings:

1. **Dry-Run Default**: The remediation tool (`python -m verification_harness.remediate`) plans and prints without writing unless `--apply` is passed explicitly. Every apply backs up the affected cells first, and `--restore` reverses the most recent apply. Only `CONFIRMED` findings are acted on.
2. **Backups & Restores**: Prior to running production updates, export database table states or create Supabase project backups (see `SIGNOFF.md`).
3. **Peer Review**: Ensure double-check procedures described in `DOUBLE_CHECK_IMPLEMENTATION.md` are followed when modifying core checks or applying bulk database updates.
